## Step 0: Migrate to Next.js (App Router, TypeScript)

Branch: `feat/nextjs-migration`. Baseline commit on `main` holds the original Vite project.

### Project setup differences found and handled

- Uploaded files were named `src (Copy)`, `index (Copy).html`, `package (Copy).json`, `package-lock (Copy).json`. Renamed to `src`, `index.html`, `package.json`, `package-lock.json` in the baseline commit.
- No `.git`, `.gitignore`, `vite.config.*` or `.env` were included. A repository was initialised and a `.gitignore` created.

### Files created

- `next.config.mjs`: `reactStrictMode: true` (matches the former `React.StrictMode` wrapper).
- `tsconfig.json`: strict mode, `@/*` alias to `src/*`.
- `next-env.d.ts`: required by Next.js. The comment lines inside it are generated by Next.js itself and rewritten on every dev or build run.
- `.env.example`: `NEXT_PUBLIC_API_URL=http://localhost:8000`.
- `src/app/layout.tsx`: root layout. `lang="en"`, title "Mukando Dashboard", viewport width and initial scale, imports `globals.css`.
- `src/app/page.tsx`: renders `ClientApp`.
- `src/app/ClientApp.tsx`: Client Component that loads `App` with `next/dynamic` and `ssr: false`. This keeps every browser-only access (`localStorage` read at import in `api.ts`, `window.location` in `App`) out of server rendering and removes any hydration mismatch.
- `src/types.ts`: shared types for roles, loan status, amounts, tokens, users, members, paginated lists, group, contributions, loans, repayments, balance, funds, summary, personal report, signup payload and field events.
- `CHANGELOG.md`.

### Files renamed

- `src/App.jsx` to `src/App.tsx`
- `src/account.jsx` to `src/account.tsx`
- `src/auth.jsx` to `src/auth.tsx`
- `src/member.jsx` to `src/member.tsx`
- `src/treasurer.jsx` to `src/treasurer.tsx`
- `src/ui.jsx` to `src/ui.tsx`
- `src/api.js` to `src/api.ts`
- `src/styles.css` to `src/app/globals.css` (contents unchanged)

### Files deleted

- `index.html`: replaced by `src/app/layout.tsx`.
- `src/main.jsx`: replaced by the Next.js entry (`layout.tsx` and `page.tsx`).
- No `vite.config.*` was present in the upload. If one exists in your copy, delete it.

### Modified behavior-neutral edits inside converted files

- `"use client"` added to `App.tsx`, `auth.tsx`, `account.tsx`, `member.tsx`, `treasurer.tsx`, `ui.tsx`. `api.ts` has none because it is only loaded through the client-only tree.
- Import specifiers changed from `./api.js`, `./ui.jsx` and similar to extensionless (`./api`, `./ui`). Webpack does not map `.js` to `.ts` or `.jsx` to `.tsx`.
- `api.ts`: `import.meta.env.VITE_API_URL` replaced by `process.env.NEXT_PUBLIC_API_URL`. Same `http://localhost:8000` fallback. Existing environments must rename `VITE_API_URL` to `NEXT_PUBLIC_API_URL`.
- `api.ts`: `JSON.parse(localStorage.getItem(KEY) as string)`. The cast only satisfies strict typing; `JSON.parse(null)` returns `null` exactly as before.
- `api.get`, `post`, `patch`, `del` and `fetchAll` became generic so responses are typed. Request and response contracts are unchanged.
- `treasurer.tsx` `GroupSettings.save`: added `if (!value) return` after `preventDefault()`. This satisfies strict null checks. The form only renders when `value` exists, so the guard is unreachable in practice.
- Error handling keeps `err.message` through `(err as Error).message`.
- Tab content lookups use `Partial<Record<TabKey, ReactNode>>` casts. Tab lists are typed `readonly [TabKey, string][]`.
- No `any` is used anywhere.

### Type assumptions to confirm against the API

- `Role` is `'TREASURER' | 'MEMBER'`. Only `'TREASURER'` is checked in the code; the member value is assumed.
- `MyReport.total_contributions`, `outstanding_balance` and `outstanding_loans`, and `LoanBalance.balance`, are typed as numbers because the code multiplies or compares them. Other money fields are `string | number`.

## 6. Unresolved items, compromises and decisions

1. **API types: confirmed by you.** The types were inferred from how the code uses the API, and you confirmed the assumptions: the member role value is `MEMBER`, and the personal report fields `total_contributions`, `outstanding_balance` and `outstanding_loans`, plus the loan `balance`, are numbers. No code change was needed.
2. **Original upload gaps.** The zip contained no `.git`, `vite.config.*`, `.env`, `public/` or tests; a repository and `.gitignore` were created, and the "(Copy)" file names were normalized in the baseline commit.
3. **Steps taken without separate approval.** At your instruction, Step 5a and 5b were delivered together, and Steps 6 and 7 were completed without waiting. The slide wording, the logo mark, the splash duration and the existing-user rule for the welcome flag were my choices.
4. **Existing-session users skip the welcome** and are marked as having seen it. A visitor who opens only a password-reset link does not set the flag, so they see the welcome flow on their next normal visit.
5. **Five stat tiles** fit in one row at 1440px but wrap 4 and 1 below about 1300px of content width. This is inherent to five tiles; it is not an overflow.
6. **Cosmetic:** in the mobile sign-in banner the illustration is cropped, so the figures' heads are partly cut off. The file can be replaced or its `object-position` adjusted in `AuthPage.css`.
7. **Not tested:** a real backend, screen-reader output, and full keyboard-only navigation of every page (verified: Tab reaches the sign-in fields with a visible 2px focus ring, and Escape closes modals).
8. **`npm audit` reports 2 advisories (1 critical, 1 high) and needs your decision.** The critical one is for `next` 14.2.35 (a list of denial-of-service, cache-poisoning and cross-site scripting issues in server-side features: the image optimizer, React Server Components, rewrites, middleware, CSP nonces); the high one is for the PostCSS copy bundled inside Next. This project is a client-rendered single page that uses no middleware, rewrites, server actions or remote images, and `next/image` is used only for local SVG files, but the advisories still apply to any server running `next start`. The only fix npm offers is Next 16, which is a breaking change that also requires React 19. I did not apply it because your rules forbid dependency upgrades that were not approved. Recommended: treat the upgrade to a patched Next release as its own approved step before deploying to production.
